Project plan · draft 3 · 22 Oct 2026 · built on Cloudflare Forge

Ferrule.

An open-source toolkit for teams leaving Stainless. It turns an OpenAPI spec and a stainless.yml into the same idiomatic Python SDK Stainless would have generated, and proves nothing public changed. It uses Cloudflare's Forge as the engine instead of building another generator. Everything runs locally and in CI: no hosted service, no account.

Leave Stainless without your users noticing. Same config, same Python SDK, proof of zero breaking changes.

License
Apache-2.0, DCO, no CLA
Engine
Cloudflare Forge, pinned dependency
Input
OpenAPI 3.x + stainless.yml
Output
Stainless-identical Python SDK
Languages
TypeScript (plugin), Python (tools, runtime)
Runs
Laptop, CI, offline
§1 · Decision

Build the missing pieces on top of Forge, not a new generator

Forge and Speakeasy already cover "an open-source SDK generator". Nobody covers "leave Stainless and change nothing for your users".

Forge (Cloudflare, Apache-2.0) parses specs and runs WebAssembly plugins, but it has no Python target, doesn't read stainless.yml, and has no migration tooling. Speakeasy is open source, but on its free path the code it puts in your SDK is AGPL, and its own Python style differs from Stainless's, so switching breaks your users. Ferrule fills exactly that gap, using Forge as a library.

What Ferrule is

  • A converter: stainless.yml → Forge overlays and extensions
  • A Forge plugin that emits Stainless-identical Python
  • Migration tools: rescue, adopt, verify, custom-code merge

What it is not

  • Not a spec parser or general generator platform
  • Not a fork of Forge
  • Not a hosted service
  • Not multi-language, until Python is proven

Best outcome

Cloudflare accepts the pieces upstream and Ferrule folds into Forge. If they don't, Ferrule stands alone as plugin plus tools, and nothing is lost.

§3 · Why build on Forge

Use it as a pinned library, not a fork, and keep it behind an adapter

OptionVerdictReason
Our own generatorNoRebuilds what Forge already does; a solo project loses that race once Forge ships Python.
Fork ForgeNoDaily upstream churn, Rust core, users would have to choose between forks. Fork only to patch a proven gap, upstream the patch, then drop the fork.
Contribute everything upstream onlyNot aloneMerged PRs come almost entirely from Cloudflare's own team, and migration tooling probably isn't their priority. Propose it, but don't wait on it.
Own repo, Forge as a dependencyYesPlugins load from any .wasm file, so nothing needs Cloudflare's approval. Upstream whatever they want.

What Forge gives us

  • Spec parsing, overlays and grouping, from npm @cloudflare/forge
  • A WebAssembly plugin interface (forge:plugin@0.3.0): the plugin receives groups, methods, models and types and returns files
  • Unknown x- extensions are passed through to plugins, which is how stainless.yml settings reach the Python plugin
  • Plugins written in TypeScript, built with npx forge-plugin build

Lock-in, and how we contain it

  • Legal: none. Apache-2.0, no account or key, released versions can't be revoked.
  • SDK users: none. Generated SDKs never depend on Forge.
  • Technical: the plugin interface is pre-1.0 and already broke once. Pin exact versions and let parity tests decide upgrades.
  • Adapter: the plugin first maps Forge's data into our own small model. Emitters only see that model, so replacing Forge means rewriting the adapter, not the emitters.
  • Unchecked: whether Forge sends telemetry. Verify in Phase 0.

Plugin limits to design around. Plugins run sandboxed (no files, network or clock), so ruff formatting and checks run after Forge. Each group is generated in isolation, so client-wide files come from the one-time generate call. Plugins see only the spec, so all stainless.yml settings must travel as extensions or overlays.

§4 · Leaving Stainless

OpenAPI + stainless.yml → the same Python SDK, proven

Stainless's own output is the specification. Every public Stainless repo has what we need to test against: api.md lists the public surface, .stats.yml records the spec and config hashes, and the last generated commit is the expected output.

# First hour for a team leaving Stainless
uvx ferrule adopt .
✓ read .stats.yml → spec URL + hash
✓ rescued spec to ./openapi.json (hash ok)
✓ converted stainless.yml → overlays
✓ copied runtime from your repo (you own it)
✓ found 3 hand edits → .ferrule/patches/
✓ generated via forge + ferrule-python
uvx ferrule verify --against v2.14.0
  public API: 0 breaking · 6 additive
  your tests: 412 passed on new output
  HTTP replay: 38/38 identical
✓ opened PR "Switch SDK generation to Ferrule"

on:

How parity is measured

  • Public API diff with griffe against the last Stainless release; target is zero breaking
  • The repo's own tests run against our output
  • HTTP replay of recorded sessions
  • Normalized text diff as a closeness percentage

Oracle repos, pinned at their last Stainless commit

  • OneBusAway/sdk-config + python-sdk: a public stainless.yml with its output, the golden pair
  • groq-python, lithic-python, perplexity-py: real SDKs with custom code
  • opencode-sdk-python: the one we know inside out

Legal guardrails. Generated Stainless SDKs are Apache-2.0 and owned by customers. Keep licence and NOTICE text, mark modified files, never use the Stainless name in the product. In adopt mode the runtime comes from the customer's own repo. Nobody who has seen the private stlc source contributes. Get a lawyer to review before 0.1; this page is not legal advice.

§5 · Differentiation

What makes teams pick this over Speakeasy or Scalar

1

Proof that nothing broke

ferrule verify prints 0 breaking / N additive against your last Stainless release. Rivals sell their own style, so they won't adopt a former rival's design as the spec.

IMPACT · EFFORTHigh · Medium
2

Spec rescue and one-command adoption

Each Stainless repo's .stats.yml points to a spec in a Stainless-owned bucket that may disappear. adopt saves it, converts the config, records hand edits and opens a PR. Rescue alone is useful to every Stainless customer, which makes it the top of the funnel.

IMPACT · EFFORTHigh · Low
3

Output you own

No licence obligations on generated code, no token, no telemetry. Contributors use a DCO, never a CLA, so the project can't be relicensed. This is the direct answer to Speakeasy's AGPL free path.

IMPACT · EFFORTHigh · Low
4

Agent context inside every wheel

SKILL.md, AGENTS.md, llms.txt and tested recipes ship with the package, locked to its version. Incumbents serve agent context from hosted docs.

IMPACT · EFFORTVery high · Low
5

A fake server in every SDK

yourapi.testing returns spec-valid fixtures, so users and agents can run code without API keys.

IMPACT · EFFORTHigh · Medium
6

Public fidelity board

Nightly regeneration of public Stainless Python repos with published scores. Launch on HN with the data.

IMPACT · EFFORTMedium · Medium

Later, once demand is proven. Errors an agent can fix on its own, an agent usability score (ferrule eval), libcst codemods for SDK users on breaking changes, and a Python MCP server from the same model.

import { definePlugin } from '@cloudflare/forge/plugin';
import { toModel } from './adapter/to-model';   // Forge → SdkModel
import { emitClient, emitGroup } from './emit';  // SdkModel → files

export const { generate, generateGroup } = definePlugin({
  generate: (forge) => emitClient(toModel.client(forge)),
  generateGroup: (group) => emitGroup(toModel.group(group)),
});
§8 · Engineering principles

Rules the code is reviewed against

These go into CLAUDE.md word for word.

Stainless output is the spec

When unsure, the oracle repos decide. Any deviation needs an ADR.

Forge stays behind the adapter

Only adapter/ imports Forge types. Emitters see our model only.

DRY across sync and async

One emitter pass with a mode flag. Type mapping lives in one function.

Runtime written once

The runtime lives in runtime/, tested once, copied into each SDK. SDKs never depend on Ferrule or Forge.

Deterministic output

Same inputs give byte-identical files. No timestamps, no LLM calls at generation time.

Pure functions

Convert and emit are pure. File and network access only in the CLI.

Diagnostics with addresses

Every error has a FER code, a pointer into the spec or config, and a suggested fix.

Upstream first

Anything generic (a Forge bug, a missing field) goes to Forge as an issue or PR, not a local workaround.

§9 · Tech stack

TypeScript where Forge runs, Python where the SDK lives

ADR 0001 · Languages · supersedes the Python-core decision in draft 2

Converter and plugin in TypeScript; runtime and migration tools in Python

Forge plugins are TypeScript compiled to WebAssembly, so the plugin is TypeScript, and the converter shares its toolchain. The runtime is Python because it ships in the SDK. The migration tools stay Python because griffe (API diff) and libcst (AST merge, codemods) are Python, and users run them with uvx.

Proposed · 25 Oct 2026 · after the Phase 4 gate · would amend ADR 0001

Move converter and plugin to Rust; keep runtime and migration tools in Python

Forge is a Rust crate: plugin execution (wasm) and the CLI are optional features, and it has a native Plugin trait (generate, generate_group) that its own TypeScript generator implements. A Rust Ferrule could depend on Forge through Cargo and run in one process, with no Node, pnpm, jco or WASM build.

PartSize todayRust?
converter/~4k lines TSYes Pure data transformation; serde fits.
python-plugin/~11k lines TSYes Native Plugin, or a WASM component against forge.wit via wit-bindgen. The golden output must stay byte-identical, which makes the port checkable.
runtime/~9k lines PythonNo It ships inside every Python SDK.
migrate/~2.5k lines PythonKeep Python griffe (verify) and libcst (merge) have no published Rust equivalent.

Gain: one native binary, faster pipeline, closer to Forge's own code. Cost: about 15k lines rewritten, a new ADR, and the native trait is an internal API that may churn more than the versioned WIT interface (compile to WASM against the WIT to avoid that). Do it as one step after the Phase 4 gate, using the existing golden files as the pass/fail check.

§15 · Agentic workflow

Claude writes most of the code; you decide and review

You

Own the model, any deviation from Stainless output, and the relationship with the Forge team. Approve golden diffs and releases.

Claude sessions

One per part (converter, plugin, runtime, migrate), each in its own worktree. They close parity gaps, triage failures, write fixtures.

CI

The referee. Merges happen when gates pass and you approve the generated-code diff.

  1. DetectNightly parity or corpus fails; an issue opens with the FER code.
  2. ReduceShrink to a minimal failing fixture.
  3. PinCommit the fixture and a failing test first.
  4. FixIn the part that owns it, or file it upstream if it's Forge's.
  5. ReviewGates pass; you read the generated-code diff.
